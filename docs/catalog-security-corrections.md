## Application dependency review

- `lib/auth/requestScope.ts:80–92` checks workspace_members before loading workspace metadata; page/API guards expose that boundary. Organization membership alone does not authorize the application workspace.
- `app/[workspaceId]/settings/reminders-actions.ts` and `settings/actions.ts` authorize workspace before settings changes; `settings/_components/RemindersSettingsSection.tsx:25–33` reads templates/rules by workspace. `lib/reminders/provisionDefaultSetup.ts` creates defaults for an explicit workspace. These flows retain member reads/writes. The debug template page loses access to foreign workspaces intentionally.
- `lib/reminders/send.ts:187–205` inserts attempt history using the authenticated server client by default, or an explicitly supplied admin client for automated execution. Valid member logs remain possible; invalid invoice lookup at `send.ts:278` may attempt a failed log with an inconsistent/nonexistent invoice. The fence/FK must reject that log; it must not become a successful send or a fabricated valid history row. `reminders.template_id` references **message_templates**, not reminder_templates: this migration does not invent a replacement FK or new template semantics.
- `app/[workspaceId]/payments/actions.ts` uses authenticated guarded RPCs for create/edit/restore. Delete/single/bulk archive directly update **archived_at only**. `clients/_actions/clientActions.ts::archiveClient` also writes only payment archive timestamps. Keeping UPDATE(archived_at) preserves those paths; triggers may set updated_at without granting the caller direct timestamp writes.
- `clients/_actions/clientActions.ts::unarchiveClient` previously cleared payment archives directly. Keeping unrestricted archived_at UPDATE would leave a restore overpayment bypass. The accompanying local change restores invoices first, completes ordered invoice/payment pagination, then calls `rpc_unarchive_payment_manual` once per archived payment. It reports failures/partial completion, refreshes all affected paths and never automatically retries rejection. This is not an atomic all-client restore; successful rows remain restored if a later RPC fails.
- Payment CSV import uses the server-admin `rpc_import_payments`; invoice import uses server-admin RPCs. Their service-role/owner operations and grants are not revoked. Legacy import execute/preview overloads are already inaccessible to all three API roles in U02. `publicInvoiceLoader.ts:121–132` uses admin/token authorization rather than anonymous base-table access; its server-side service-role reads remain available.
- No application INSERT/UPDATE/DELETE against the financial views was found. Their current join/aggregate definitions are not automatically updatable, but revoking write grants prevents retaining an unnecessary future write path. Service-role view access remains unchanged.
